# Changelog

All notable changes to this project will be documented in this file.

## [1.14.0] - 2026-09-15

> Field test report of 2026-09-15 (`docs/mcp-test-report-20260915.md`, 9 findings: 1 Blocker / 2 High / 3 Medium / 3 Low), from a session that tried to build a Cloud Functions cron scheduler to start/stop a server. **Every Cloud Functions write call failed with gateway error 80031**, while every read call on the same credentials succeeded — and the failure text carried no request ID, so the tester could not tell an MCP bug from a platform outage. Specs re-derived from the official [Cloud Functions API](https://api.ncloud-docs.com/docs/compute-cloudfunctions) at **version 2.1** (per-operation pages `compute-cloudfunctions-v2-*`).
>
> **Root cause of the blocker, as far as the code shows it:** the module targeted the **v2.0 path prefix `/api/v2/…`** (v2.1 is `/ncf/api/v2/…`, same base URL) and sent request bodies that matched **neither** version — `raw_http`/`custom_options` where both versions spell the fields `raw-http`/`custom-options`, top-level `vpc_no`/`subnet_no` where v2.1 wants `vpc: [{vpcNo, subnetNo}]`, `limits.*`/`exec.binary` optional where the spec marks them required, a `trigger` wrapper object around the trigger body, and `/link` + `actionName` where v2.1 is `/link-action` + `{action, package}`. Read operations have no body, which is why they worked on the old prefix. On top of that, **all five runtimes the tester tried (`python:3.11`, `python:3.9`, `nodejs:16`) are either past their 2025-09-18 end-of-support date or not a documented runtime at all**, and the runtime guide says new actions on ended runtimes are refused. Whether 80031 was the gateway's response to the malformed body, to the retired runtime, or to a genuine outage cannot be settled from the report alone; the request is now spec-conformant on every axis the report exercised, and a failure will now carry the request ID needed to ask Ncloud.
>
> **Not live-verified.** This release was built against the documentation only; see Notes for what a live run should check first.
>
> **Breaking (Cloud Functions only):** `ncloud_functions_create_action` drops the `web` boolean in favour of a `type` parameter (`basic` | `web` | `sequence` | `sequence-web`, a v2.1 query parameter), makes `vpc_no`/`subnet_no` mandatory for basic/web actions on `platform=vpc`, and refuses end-of-support runtimes unless `allowDeprecatedRuntime=true`. `ncloud_functions_create_trigger` replaces the free-form `trigger` object with typed, top-level fields (`cronOption`, `credential`, `events`, `link`, `insightLink`, `objectStorageLink`, `sourceCommitLink`, `secretManagerLink`). `ncloud_functions_link_trigger_action` / `unlink_trigger_action` take `actionName` + optional `packageName` instead of a single `"pkg/action"` string (the old form is still accepted and split). The five activation-list tools take `start`/`end` as **millisecond Unix timestamps (integers)**, which is what the API defines; the previous `yyyy-MM-ddTHH:mm:ss` strings were never valid. Every affected write tool was non-functional before this release, so no working call changes behaviour. `ncloud_get_server_detail` changes its response shape (see Changed).

### Fixed
- **F-01 · All 22 Cloud Functions tools now call the v2.1 path `/ncf/api/v2/…`.** A source-level test fails if the v2.0 prefix reappears. Region base URLs (KR / SG / JP) are unchanged.
- **`ncloud_functions_create_action` sends the v2.1 Put Action contract.** `type` goes in the query string; the body carries `exec {kind, binary, code, main, imageUri?}`, `limits {timeout, memory}` (defaults 60000 ms / 128 MB, the API marks both required), `vpc: [{vpcNo, subnetNo}]` on `platform=vpc`, hyphenated `raw-http` / `custom-options` (web types only — passing them on a basic action is refused before the call), and `parameters` / `description`. Sequence types send `exec {kind: "sequence", components}` only, and each component must be `{packageName}/{actionName}`. `java*`/`dotnet*` without `exec_binary=true` and `custom image` without `exec_imageUri` are refused with the reason. New optional `exec_imageUri` for the Custom Image runtime.
- **`ncloud_functions_create_trigger` sends the v2.1 Put Trigger contract** (flat body, `type` as query; `secret_manager` added as a sixth type). Each type's required fields are checked before the call, and a field belonging to a *different* type is refused rather than silently dropped. The GitHub access token echoed back in the response is masked.
- **`ncloud_functions_link_trigger_action` / `unlink_trigger_action` use `POST`/`DELETE /ncf/api/v2/triggers/{name}/link-action` with body `{action, package}`** (the unlink previously sent `actionName` as a query parameter, which the API does not read).
- **Activation list tools (`get_action_activations`, `get_trigger_activations`, `get_activations`) take `start`/`end` as millisecond timestamps** and document the one-month window and the `pageSize=20` default.
- **F-02 · Failed API calls now carry the diagnostics the report asked for.** Every `API 호출 실패` / `API call failed` message ends with: `HTTP 상태`, the request as `METHOD /path` (query string deliberately omitted — it can carry passwords), the gateway's `x-ncp-apigw-request-id` and `x-ncp-trace-id` when present, `error.details` when the service supplies one, a `재시도 가능` verdict (yes for 429/5xx or "try again"-style text, no otherwise) and the observation time in ISO 8601. The first three lines of the message are unchanged, so existing parsers and tests still match. Applies to `request()` and `requestRaw()` alike, i.e. every service. The empty-body error path also lists `x-ncp-apigw-request-id` among its diagnostic headers.
- **F-04 · Gateway HTML in error messages is converted to plain text** (`<br>` → newline, other tags removed, entities decoded). The conversion only triggers on known HTML tag names (`br`, `strong`, `div`, `li`, …), so a service message that uses angle brackets as placeholders (`<A>`) is left untouched.

### Security
- **F-03 · `ncloud_functions_get_action` redacts secrets in the returned source code by default.** Hard-coded assignments to names like `access_key`, `secret_key`, `api_key`, `password`, `token`, `client_secret` (Python/JS/JSON/YAML/.env spellings, quoted values ≥ 8 chars), Ncloud `ncp_iam_*` keys, `AKIA…` ids, `Bearer …` tokens and PEM private-key blocks are replaced with `<REDACTED:n chars>`; the response gains `secretsRedacted: true` and `redactedCount` so the model does not mistake it for truncated code. `includeSecrets=true` returns the raw code but still attaches a `secretsDetected` count and a warning. Base64 (`exec.binary=true`) archives are not scanned and say so. The same redaction is applied to the code echoed by `create_action`. Helper: `src/tools/_secrets.ts`. (F-09 — the customer's own hard-coded keys — is out of scope for the server; rotate them.)

### Added
- **F-08 · `dryRun` on `ncloud_functions_create_package`, `create_action` and `create_trigger`**, rendering the exact `PUT` endpoint, query and body through the standard `_dryrun.ts` preview. Client-side validation (runtime, required fields, cron shape) runs before the preview, so a request that would be refused is refused in dry-run too.
- **F-06 · Cron trigger format is documented and validated.** `cronOption` must be a 5-field UNIX expression (`minute hour day-of-month month day-of-week`); anything else is refused before the call. `create_trigger`, `get_trigger` (cron type) and the dry-run preview attach a `cronFormat` note stating that **the expression is evaluated in KST (UTC+9)** — the official cron guide does not document the time zone, so this was settled by a live probe on 2026-09-15 (KR): a `*/5 * * * *` trigger fired at 22:30:00.038 / 22:35:00.049 KST and a `41 22 * * *` trigger fired at 22:41:00.044 KST. No `timezone` field is invented, because the API does not return one.
- `ncloud_functions_create_action` refuses runtimes past their documented end of support (`nodejs:6/8/12/16`, `python:3.6/3.7/3.11`, `php:7.1`, `go:1.11`, ended 2025-09-18) with the current list of supported runtimes (`nodejs:22`, `python:3.13`, `java`, `java:21`, `swift:3.1.1`, `php:7.3`, `go:1.19`, `dotnet:2.2`, `custom image`); `allowDeprecatedRuntime=true` overrides.

### Changed
- **F-05 · `ncloud_get_server_detail` now returns something the list does not.** The Server API's detail payload is field-for-field identical to the list entry, so the tool now also fetches the attached block storages (summarised: name, size in GB, type, volume type, status, device, **`blockStorageProductCode`** for pricing) and the instance tags, returned as `{ serverInstance, blockStorages, tags, pricingHint }`. The two extra reads are best-effort: a failure lands in `relatedErrors` and the server detail is still returned. `includeRelated=false` gives the bare payload. Billing type and contract are not available from the Server API; the `pricingHint` says to use `ncloud_get_product_price_list` with the product codes.
- **F-07 · `ncloud_list_public_ips` / `get_public_ip_detail` state in their description that the Public IP API returns no product code** and how to price one (`productName='Public IP'`). The API payload cannot be extended from the client side.

### Removed
- **The "known issue: 300 Not Found" warning on `ncloud_ses_get_cluster_server_images` and `ncloud_cdss_get_cluster_server_images`, and the diagnosis both tools appended to a 300 failure.** 1.13.0 shipped them because the documented `GET …/cluster/getClusterServerImageList` route returned 300 on the live KR API (2026-09-02) and nothing in the documentation explained why. On 2026-09-15 the user confirmed that the SES and CDSS operations that had been failing now work, so the warning was stale and would have sent callers to the console for an image code the tool returns. The descriptions now say what the image code feeds (`get_server_specs` / `get_server_spec_list`, `get_subnet_list_g3`, `create_cluster_g3`); errors pass through unchanged. The rest of 1.13.0's SES/CDSS corrections are hereby live-confirmed as well.

Handlers are invoked through the registered zod `inputSchema` so defaults apply as in the SDK.
- `src/tools/_secrets.test.ts` (7): the report's Python pattern, JS/JSON/YAML spellings, value-shape patterns, false-positive guards, `redactAtPath` immutability.
- `src/client/ncloud-client-diag.test.ts` (10): `stripHtml` on the real 80031 payload, entity decoding, plain-text passthrough; diagnostics on `requestRaw` and `request` failures, absent request-id, 5xx retryable verdict, `error.details`, `NCLOUD_LANG=en`, header-less mock responses.
- `src/tools/compute-server-detail.test.ts` (4): enriched shape, partial failure → `relatedErrors`, `includeRelated=false`, empty list.
- One existing assertion updated: the analytics-envelope test now checks `에러 코드: 3` / not `에러 코드: 200` instead of "message contains no `200`", since the diagnostics legitimately print `HTTP 상태: 200` for that class of rejection.

### Notes
- **Live-verified on 2026-09-15 (KR region, VPC 21538, subnet 299511) — see `TESTPLAN_v1.14.0-cloudfunctions.md` / `REPORT_test-result_v1.14.0-cloudfunctions.md` in the infra workspace.** `create_package` → `create_action` (`python:3.13`, `type=basic`, vpc attached) → `invoke_action` (`{ok:true}`, 254 ms) → `create_trigger type=cron` → `link_trigger_action` (`status=active`) → `invoke_trigger` → `get_trigger_activations` all returned 2xx: **the 80031 blocker (F-01) is gone.** The dry-run previews matched the bodies that were actually sent. Both client guards fired without calling the API (deprecated `python:3.11`; missing `vpc_no`/`subnet_no`). `get_action` redacted the two hard-coded keys of an existing action (`secretsRedacted=true`, `redactedCount=2`). A `PUT` on an existing trigger kept its linked action (`rules … active`). Three observations: (1) the gateway's request-id header is **`x-ncp-trace-id`**, which the failure message already prints (no `x-ncp-apigw-request-id` is returned); (2) `get_trigger_activation_detail` returned `80518 TRIGGER_ACTIVATION_NOT_FOUND` for ~30 s after the activation appeared in the list — a propagation delay, retry after a short wait; (3) whether the `vpc` array is truly mandatory for VPC actions was not probed (no override exists; the console decides) — the guard stays.
- **Cron time zone: KST.** Settled by the probe above; `CRON_NOTE_EN`, the `cronOption` description and `get_trigger`'s description now say so. The two `get_*_activation_detail` descriptions mention the ~30-40 s propagation delay observed after an invocation.
- Not exercised live: `get_action includeSecrets=true` (the client's safety classifier blocked the call — not a tool defect), github/insight/object_storage/source_commit/secret_manager trigger types, sequence actions, and the `vpc`-array-mandatory question.

## [1.13.0] - 2026-09-06

> Field bug report of 2026-09-01 (7 defects: 4 Blocker / 2 High / 1 Low), found while creating and deleting NAS, five Cloud DB engines, Cloud Hadoop, SES, CDSS and VPC Peering on a real KR account. Every defect had the same root cause — **the input schema did not match the API's actual parameter contract** — in three shapes: a field name that was never mapped, required parameters missing from the schema entirely, and a GET endpoint called with a POST body. **Three services could not be created through MCP at all**: Cloud DB for Cache, Search Engine Service, and Cloud Data Streaming Service. Specs re-derived from the official API docs for [Cloud DB for Cache](https://api.ncloud-docs.com/docs/database-vcache), [Search Engine Service](https://api.ncloud-docs.com/docs/analytics-vpcsearchengine) and [Cloud Data Streaming Service](https://api.ncloud-docs.com/docs/analytics-clouddatastreamingservice).
>
> **Live-verified against a real KR account over nine rounds, 2026-09-02~05 KST.** The first rounds cleared the field report and turned up 13 further defects in the same files; a path sweep then found that **36 of the 58 cluster-dependent SES/CDSS tools had no route at all**; and a real CDSS cluster finally exercised the parameter contracts that no amount of sweeping could reach. Cache creation and the whole CDSS surface now work through MCP alone. See Tests below for exactly what was and was not exercised — the coverage is uneven and stated tool by tool.
>
> **Breaking:** several Cache tools have renamed or newly-required parameters, and phantom parameters the API never accepted were removed. Every affected tool was non-functional before this release, so no working call changes behaviour — but a caller passing the old names will now get a schema error instead of a silent failure.

### Fixed
- **`ncloud_create_cache_instance` never sent the config group — Cloud DB for Cache could not be created.** The schema's `cloudCacheConfigGroupNo` was passed straight through to the query string, but the API's parameter is **`configGroupNo`**; supplying a valid group produced the identical `900 Required field is not specified. location : configGroupNo` as supplying nothing. The parameter is renamed and now **required** (it was marked optional, which invited callers to omit a value the API demands). Three more schema defects surfaced while re-deriving the tool from the spec: `cloudCacheServerNamePrefix` and **`cloudCacheModeCode`** (`SIMPLE` | `CLUSTER`) are required by the API — the latter was absent from the schema altogether — and **`isAutomaticFailover` is not an API parameter at all** (the redundancy flag is `isHa`), so it was silently dropped on every call. `isAutomaticBackup`, `engineVersionCode`, `cloudCacheDbmsCode` (`Redis` | `Valkey`) and `generationCode` (`G2` | `G3`) were added, `backupFileRetentionPeriod` corrected to the documented 1–7 days (it claimed 1–30), and `shardCount` / `shardCopyCount` bounded to 3–10 / 0–4 with a note that they apply to `CLUSTER` mode only. A call with `isBackup=true` and `isAutomaticBackup=false` but no `backupTime` is now rejected before it reaches the API.
- **`ncloud_create_cache_config_group` had no field for `cloudCacheVersion`, and two of its four fields were the wrong names.** The workaround for the defect above — create a fresh config group — was blocked by `900 Required field is not specified. location : cloudCacheVersion`, with nowhere in the schema to put a value. Cloud DB for Cache therefore had **no path to creation through MCP at all**. `cloudCacheVersion` is now a required parameter, and its valid values were already listable via `ncloud_list_cache_config_group_versions` (16 of them, e.g. `8.1.6-simple`, `7.2.11-cluster` — the suffix is the mode, `-simple` = Standalone). Comparing the rest against the spec found two more send-time mismatches that would have failed the next call anyway: `cloudCacheConfigGroupName` → **`configGroupName`** and `description` → **`configGroupDescription`**. `cloudCacheImageProductCode` was removed — `createCloudCacheConfigGroup` has no such parameter — and the documented `cloudCacheDbmsCode` was added.
- **`ncloud_create_cache_instance` reported a port and backup setting it had not sent.** When those parameters were omitted the dry-run preview and the creation summary filled in `6379` / `isBackup: true` while `apiParams` carried neither, so the server's own defaults applied and could differ from what the tool reported — a caller who then wrote ACG rules for port 6379 would get a connection that silently fails. The summary now prefers the port in the API response and otherwise says "server default"; the preview shows only what is actually transmitted, with one note explaining that anything absent is left to the server.
- **`ncloud_ses_get_node_products` sent a POST body to a GET endpoint — 300 Not Found.** `getNodeProductList` is `GET /api/v2/cluster/getNodeProductList` with query parameters; the tool sent `softwareProductCode` as a JSON body, so the API gateway never matched a route. It also takes a second **required** parameter the schema lacked, `subnetNo`. Both are now sent as query parameters. This blocked `dataNodeProductCode` — a required input of SES cluster creation.
- **`ncloud_ses_get_subnet_list` omitted `softwareProductCode`, which the endpoint requires.** It sent only `vpcNo` and got `400 유효하지 않은 OS 타입입니다` ("invalid OS type") — the error that identified this whole endpoint family as OS-type dependent. `ncloud_ses_get_subnet_list_g3` had the same defect (its POST body carried only `vpcNo`) and also gained the documented optional `isPrivate`. `ncloud_ses_get_cluster_server_images` gained the documented optional `generationCode` (`G3`).
- **Six CDSS lookup tools took no input at all, and one of them pointed at a path that does not exist.** Every one of them returned 300:
  - `ncloud_cdss_get_kafka_versions` called `/cluster/getKafkaVersionList`; the operation is **`getCDSSVersionList`**. This blocked `kafkaVersionCode`, a required input of both cluster and config-group creation.
  - `ncloud_cdss_list_config_groups` called `GET /configGroup/getConfigGroupList`; the operation is **`POST /configGroup/getKafkaVersionConfigGroupList`** with a **required `kafkaVersionCode`** in the body. It gained `pageNo`/`pageSize`.
  - `ncloud_cdss_get_node_products` is `POST` with `softwareProductCode` **and `subnetNo`** in the body; `ncloud_cdss_get_subnet_list` is `POST` with `softwareProductCode` **and `vpcNo`** (it previously sent `vpcNo` as an optional query parameter on a GET); `ncloud_cdss_get_server_spec_list` (G3) is `POST` with `softwareProductCode`. All three were `GET` with an empty schema.
  - `ncloud_cdss_get_cluster_server_images` gained the documented optional `generationCode`.
- **`ncloud_ses_create_cluster_g3` named three node parameters that the API does not have, and omitted two it requires.** The same comparison, run against SES's five documented G3 operations, found the KVM create tool sending `managerNodeServerSpecCode`, `dataNodeServerSpecCode` and `masterNodeServerSpecCode` where `createKvmSearchEngineCluster` takes **`managerNodeProductCode`**, **`dataNodeProductCode`** and **`masterNodeProductCode`** — B-1's failure shape again, in a tool nobody had exercised. `hypervisorCode` and `generationCode` are required and were absent from the schema entirely, so the call could not have succeeded even with the names fixed. Also added the documented optional `dataNodeStorageInfraResourceDetailTypeCode` and `serverSpecCode` (optional here, though the CDSS G3 create makes it required), corrected `dataNodeStorageSize` to 100-16000 GB (the schema said 2000), and bounded `dataNodeCount`. `isMasterOnlyNodeActivated=true` makes the three `masterNode*` values conditionally required; a call missing any of them is now rejected before the API sees it, naming which.
- **`ncloud_hadoop_list_target_subnets` was missing `cloudHadoopImageProductCode`** and failed with `900 Required field is not specified`. Both it and `vpcNo` are required by `getCloudHadoopTargetSubnetList` and are now required in the schema; the documented optional `isPublic` was added. `zoneCode` was removed — it is not a parameter of this API and was silently ignored. (Lowest-severity of the seven: the generic `ncloud_list_subnets` was a complete substitute, so Hadoop creation was never blocked.)
- **The live run exposed that `ncloud_delete_cache_config_group` carried B-1's defect verbatim, and a full parameter-name audit of the file found eleven more.** The delete tool's schema took `cloudCacheConfigGroupNo` and passed it straight to the query string — the same rename B-1 fixed on `create_cache_instance`, failing with the same `900 … location : configGroupNo`, in the same file, twenty lines above the comment explaining the rename. The consequence was that a config group could now be *created* through MCP but not *deleted*, so the verification run's own cleanup had to finish in the console. Renaming a parameter clearly has to cover a resource's whole create/delete/get family, so every one of the file's 22 tools was compared against its spec page. The other eleven:
  - **`ncloud_get_cache_target_subnets` asked for the wrong resource entirely.** It required `cloudCacheInstanceNo` — not a parameter of `getCloudCacheTargetSubnetList` — while both of the API's required parameters (`vpcNo`, `cloudCacheImageProductCode`) were absent. It could never have returned subnets, and it is the tool a caller reaches for while assembling a `create_cache_instance` call. Now takes the two documented required parameters plus the optional `isPublic`.
  - **`ncloud_delete_cache_manual_backup` could never have deleted anything.** Manual backups are addressed by instance number plus file names (`fileNameList.N`), not by a backup ID; the tool's only parameter was `cloudCacheManualBackupNo`, which the API does not define. A destructive tool that has never worked is at least fail-safe, but it also meant manual backups were unreclaimable. It now takes `cloudCacheInstanceNo` + a `fileNameList` array (min 1), serialized as `fileNameList.1`, `fileNameList.2`, … and names the files in its confirm prompt.
  - **`ncloud_export_cache_backup` sent four parameters that do not exist and omitted two that are required.** `exportBackupToObjectStorage` takes `cloudCacheInstanceNo`, `fileName`, `backupTypeMode` (`SYSTEM` | `MANUAL`) and `bucketName`; the tool sent `cloudCacheServerInstanceNo`, `folderPath` and an indexed `cloudCacheExportObjectList[].fullObjectName` list, with no `fileName` or `backupTypeMode` at all. Rewritten to the documented single-file contract.
  - **`ncloud_list_cache_manual_backup_details` took a backup number where the API takes an instance number**, so it always failed with the required-field error.
  - **`ncloud_list_cache_buckets` omitted `cloudCacheInstanceNo`**, which `getCloudCacheBucketList` requires — the bucket list feeding the export tool above was itself unreachable.
  - **`ncloud_create_cache_manual_backup` forced a `cloudCacheManualBackupName`** that the API does not accept. The server assigns the file name; the description now points at `ncloud_list_cache_manual_backup_details` to read it back.
  - **`ncloud_list_cache_backup_details` required a `cloudCacheServerInstanceNo`** the API does not define — a second value the caller had to find for nothing.
  - **`ncloud_list_cache_backups` and `ncloud_list_cache_manual_backups` advertised filters the API does not have.** Both operations take only `regionCode`; the tools required or offered `cloudCacheInstanceNo` and (for the latter) `pageNo`/`pageSize`, so a caller filtering by instance silently got the whole region back. The phantom parameters are gone and both descriptions name the per-instance detail tool instead.
  - **`ncloud_list_cache_config_groups` offered pagination the API does not support and hid the seven filters it does.** `pageNo`/`pageSize` were ignored; `cloudCacheInstanceNo`, `cloudCacheServiceName`, `configGroupNo`, `configGroupName`, `cloudCacheImageProductCode`, `cloudCacheModeCode` and `cloudCacheDbmsCode` are now exposed.
  - **`ncloud_list_cache_instances` was missing seven documented filters** (`zoneCode`, `vpcNo`, `subnetNo`, `cloudCacheServerName`, `cloudCacheServerInstanceNoList`, `generationCode`, `cloudCacheDbmsCode`), and `pageSize` is conditionally required whenever `pageNo` is given — a `pageNo`-only call is now rejected before it reaches the API.
  - **`ncloud_get_cache_image_products`, `ncloud_get_cache_products` and `ncloud_list_cache_config_group_versions` gained their documented optional filters** (`productCode` / `exclusionProductCode` / `generationCode` / `zoneCode` / `cloudCacheDbmsCode`).
- **`ncloud_cdss_get_config_group_detail` pointed at a path that does not exist.** It called `GET /configGroup/getConfigGroupDetail/{configGroupNo}` and returned 300 — the same class of routing defect as B-6's two, missed because the tool was not in the field report. The operation is `POST /configGroup/getKafkaConfigGroup/{configGroupNo}` with a **required `kafkaVersionCode` in the body**, which the tool now takes. The live plan predicted this one from the doc index before the run confirmed it.
- **Three more CDSS Config Group tools pointed at operation names that do not exist.** After `getConfigGroupList` and `getConfigGroupDetail` both turned out to be invented (see above), the whole Config Group section was compared against its nine documented operations — and three of the five remaining tools were wrong the same way. All three would have returned 300:
  - **`ncloud_cdss_get_kafka_config`** called `GET /configGroup/getKafkaConfig/{configGroupNo}` with no body. The operation is **`POST /configGroup/getKafkaConfigGroupDetailList/{configGroupNo}`** with a required `kafkaVersionCode`.
  - **`ncloud_cdss_apply_config_group`** called `POST /configGroup/applyConfigGroup/{configGroupNo}`. The operation is **`setClusterKafkaConfigGroup`**, and it needs `kafkaVersionCode` in the body alongside `serviceGroupInstanceNo` — the version code was missing entirely.
  - **`ncloud_cdss_change_kafka_config`** was wrong in four ways at once: `PUT` instead of `POST`, `changeKafkaConfig` instead of **`setKafkaConfigGroupDetail`**, no `kafkaVersionCode`, and a free-form `kafkaConfig` key/value map where the API takes **fifteen typed fields** (`autoCreateTopicsEnable`, `logRetentionHours`, `numPartitions`, …) plus an `additionalKafkaConfigGroupDetailList` array for anything without a named field. The tool now exposes the named settings individually and maps an `additionalSettings` array onto that list.
  - `ncloud_cdss_create_config_group` also typed `kafkaVersionCode` as a string while every sibling used a number; it is now a number throughout, with the documented length limits on `configGroupName` and `description`.
  - **Root cause worth naming:** five of the seven Config Group tools used a plausible-sounding operation name (`getXxxDetail`, `applyXxx`, `changeXxx`) rather than the documented one. A test now sweeps every Config Group tool's request path and fails if any of the five invented names reappears.
- **`ncloud_create_cache_instance` now rejects a `cloudCacheModeCode` that contradicts the config group before calling the API.** A config group's version carries its mode as a suffix (`7.2.11-simple` / `-cluster`) while instance creation passes `cloudCacheModeCode` separately, and what the server does when the two disagree is undocumented — the live run could not settle it without paying for a second instance. Rather than leave a silent mismatch (the same failure shape as B-3), the tool now probes `getCloudCacheConfigGroupList` with `configGroupNo` + `cloudCacheModeCode`; if that matches nothing but the group exists under any mode, the call is refused with both values named. The probe uses only documented filters, never inspects a response field name it depends on, and **any failure of the probe itself lets the original call proceed** — a diagnostic must not break a valid create. Skipped entirely on `dryRun`.

- **An HTTP 200 carrying `code != 0` was treated as success.** The analytics envelope (`{code, message, result}`) uses `code: 0` for success, but not every rejection comes with an HTTP error status: CDSS returns `200 {code: 3, message: "numPartitions has an error : …", result: null}` when a value falls outside its documented `range`. `parseBodyAndHandle` only consulted `response.ok`, so that reached the caller as an ordinary result with no `isError` — while the *same* class of rejection delivered as 400 or 500 was flagged correctly. Anything reading `isError` rather than the prose (an agent loop, a script) would have taken the refusal for a success. The client now recognises the envelope, and `handleErrorResponse` reports the envelope's `code` instead of the HTTP status, so the message says `3` rather than a misleading `200`. **The check is deliberately narrow** — numeric `code`, non-empty string `message`, and `result` explicitly null/undefined — because this client is shared by every service and a broader rule would turn some other API's success into an error. Known gap it does not catch: a non-zero `code` returned alongside real data. Six tests pin both directions, including a string `"0000"` code, a `code: 200` with a populated `result`, and an ordinary Ncloud `*Response` envelope.
- **`ncloud_cdss_delete_config_group`'s confirm prompt now names the tool that lists the clusters still using the group.** Putting that guidance only in the tool description left it out of the one message a caller sees *after* deciding to delete — the moment it is most useful. ### Security
- **Timeout errors and debug logs carried the full request URL, query string included — which for many Ncloud APIs means a password.** Ncloud exposes creation over GET, so `create_mysql_instance`, `create_mongodb_instance`, `create_mssql_instance`, `create_postgresql_instance`, the user add/change tools, `create_nas_volume`'s `cifsUserPassword`, `hadoop_create_cluster` and `get_root_password`'s RSA `privateKey` all travel in the query string. On timeout that URL went into the thrown message, which is returned verbatim to the MCP client; `NCLOUD_DEBUG=1` wrote it to stderr on every retry. Both now go through `redactUrl`, which drops everything after `?` and keeps the path — the path says which API failed and carries no secret. This predates the release and is unchanged from v1.12.0, so it is not a regression, but it is the same failure mode as the preview leak below and was cheap to close in the same release.
- **Dry-run previews would have printed database and account passwords in clear text.** Making previews render the real request object had a consequence the change itself did not account for: the hand-written previews it replaced listed a chosen subset of fields, and none of them chose the password. Rendering the request verbatim put `cloudMysqlUserPassword`, `cloudMongoDbUserPassword`, `cloudMssqlUserPassword`, `cloudPostgresqlUserPassword`, the NAS `cifsUserPassword` and the sub-account login `password` into text returned to the MCP client — where it lands in the conversation and in any transcript kept of it. `dryRunPreview` now redacts any key matching `pass(word)?|secret|privatekey|credential`, walking nested objects and arrays so list-shaped bodies (`cloudMysqlUserList[].password`) are covered too, and replaces the value with `(redacted, N chars)` so the preview still shows that a value will be sent. Identifiers and pagination tokens (`accessKey`, `loginId`, `continuationToken`) stay visible — they are what a preview exists to confirm. Caught by the pre-release security review of this branch, not by any test or live round.

### Notes
- **`ncloud_ses_get_server_specs` was reported as broken but its transport was already correct — the live run confirmed it.** The report grouped it with `ses_get_node_products` as "POST to a GET endpoint", but `getServerSpecList` (G3) genuinely is `POST` with a JSON body, and so is `getVpcAvailableSubnetList`. Feeding it a G2 OS code now returns **400 "유효하지 않은 OS 타입입니다"**, not 300 — and that distinction settles it: a 300 means the gateway found no route, while a 400 with a domain message means the request reached the service and was rejected on its contents. So POST works and the field 300 came from the G2 code, exactly as assumed; the transport stays as documented. `getVpcAvailableSubnetList` returns the same 400, so both POST tools agree. The other half of the check — that a G3 code returns 200 — remains unverified, blocked by the defect below.
- **⚠️ `getClusterServerImageList` returns 300 Not Found on both services and this release does not fix it.** The Korean and English pages for both services specify `GET /api/v{2,1}/cluster/getClusterServerImageList` with no required parameter, which is precisely what the tools send, so there is nothing in the documentation left to correct against — and the route is absent rather than gated, because `ncloud_ses_get_server_generations` and `ncloud_cdss_get_server_generations` both return `G3 (KVM)` for this account. Rather than guess at a replacement path, both tools **carry the limitation in their description and attach a diagnosis to the 300**, stating that the documented endpoint has no route and that this is not a missing-G3-entitlement problem. Non-300 errors pass through untouched.
  - **What this does *not* block:** the only thing lost is the convenience of listing image codes. Every downstream G3 tool takes the code as a parameter, and each spec page's own curl sample carries a concrete one (`SW.VCDSS.OS.LNX64.ROCKY.08.G003`, `SW.VELST.OS.LNX64.ROCKY.08.G003`), so `get_server_specs`, `get_subnet_list_g3` and the G3 create tools remain callable. An earlier draft of this entry claimed the whole G3 path was unreachable; that was wrong.

- **Cache's create/delete/get families disagreed with each other, not just with the API.** Eleven of the twelve parameter defects above were in tools the field report never exercised, and they were found only by comparing every operation in the file against its spec page after the live run exposed the twelfth. Two lessons are worth carrying forward: a renamed parameter has to be chased across the resource's whole tool family in the same commit, and **a phantom parameter is worse than a missing one** — `get_cache_target_subnets` demanding an instance number looked like a working tool with an odd signature, which is why it survived several releases.
- **`softwareProductCode` is the pivot for SES and CDSS cluster creation.** Node products, server specs and subnets are all filtered by OS image, which is why the empty-schema lookups failed as a group while their sibling `getOsProductList` — genuinely parameterless — worked. Discovery order is now: OS products (or cluster server images for G3) → VPC → subnets → node products / server specs.
- **The remaining sweeps from the report were run.** The `requestRaw("POST", …)` audit over every tool file found only the two SES calls named above, both confirmed correct against the docs; the empty-schema (`{}`) audit over SES and CDSS left nine tools, all of which the field report's control group confirmed working (`ses_get_versions`, `ses_get_os_products`, `cdss_get_os_products`, both `get_server_generations`, the two `get_vpc_list`, `ses_get_login_keys`) plus the now-corrected `cdss_get_kafka_versions`.
- **What the server does with a mismatched `cloudCacheModeCode` is now unknowable through MCP, and that is fine.** Confirming it would have needed a second instance at double the cost, so the guard was added instead — and with the guard in place a mismatched combination never reaches the server, so its behaviour no longer affects anyone. Treated as permanently unverified rather than as an open question; anyone who needs the answer has to go around MCP with curl or the console. The G3 code paths listed above could not be reached at all.
- **CDSS validates the `configGroupNo` ↔ `kafkaVersionCode` pair itself, so no client-side guard was added there.** This is the same shape of undocumented interaction as Cache's mode-vs-suffix problem, and it was checked the same way — but the answer came out opposite. Passing a valid Kafka version belonging to a *different* group returns `400 Invalid ConfigGroup`, and passing a version code that does not exist returns `400 Invalid kafka Version Code`; the server distinguishes the two failures and names the cause. Cache got a guard because the server might have accepted a mismatch silently; adding one here would only risk blocking calls that should go through. **The guard belongs where the server is silent, not wherever two parameters could disagree.**
- **The MCP SDK drops unknown input keys silently rather than rejecting them.** Observed while checking that the removed phantom parameters were really gone: a call that supplied the old `cloudCacheServerInstanceNo` and `cloudCacheExportObjectList` alongside valid required fields failed on the *valid* field's format and never mentioned the phantom ones, so they were stripped before the request. That is a useful safety property — a stale caller cannot leak a meaningless value to the API — but it also means removing a parameter gives that caller no feedback. The real defence for the renamed tools is that the old parameter alone no longer satisfies the required set, so those calls are refused outright.
- **The gateway's status code was the key diagnostic, and mixing two failures into one is what produced the field report's single misclassification.** `300` means the API gateway matched no route, so the path or operation name is wrong; `400`/`500` with a service message means the route was fine and the payload was not. B-6's two path defects and the `getClusterServerImageList` breakage are the former; the `getServerSpecList` "POST" report was the latter, misread as the former. Recording the status code alongside every defect makes the two separable on sight.
- **The 36 corrected paths were re-swept and 33 came back clean.** The remaining three needed a second pass, and two of them had been "fixed" wrongly the first time — worth recording, because both wrong turns were inferences that looked well-supported:
  - **`cdss_reset_cmak_password` is `resetCMAKPassword`, and the spec page is wrong.** It documents `resetMGMTPassword` down to its curl sample; that route does not exist. The real name capitalises CMAK exactly as `restartCMAKService` does — a convention already visible in this same file. **This is the one place in this release where the documentation itself was wrong**, as opposed to the gateway lacking a documented route. The re-sweep also proposed switching the method to GET, since six sibling single-action operations are GET; declining that turned out to be right, because the fix was the name alone and GET would have put the password into a query string that `NCLOUD_DEBUG=1` writes to stderr — while still being broken.
  - **`ses_change_disk_size` takes no path segment.** A previous pass added one by analogy with the sibling node operations, which was wrong in both directions: the spec has no segment, and the segmented form 300'd live too. Re-reading the spec verbatim also showed both fields are `Integer`, so `serviceGroupInstanceNo` is a number here rather than the string used elsewhere in the file — it is a body field, not a path segment.

- **Reading the settings back settled what `change_kafka_config`'s rewritten body has to look like.** Each entry carries a camelCase `configNameKey` (`autoCreateTopicsEnable`) beside the dotted `configName` (`auto.create.topics.enable`), and those keys map **1:1 onto the fifteen named parameters** — so for a stock group there is nothing left for `additionalSettings` to carry, and that path stays unexercised until a group with non-standard settings turns up. Two response fields the tool descriptions now point at: `range` gives each setting's valid bounds (`num.partitions` is `1~128`, `log.retention.hours` is `1~168` with the default already at the ceiling), and **`modifyYn` marks settings that cannot be changed at all** — `authorizer.class.name` is the one such setting in a stock group.
- **Three of the four defects the last live round found share one shape: the API answers `SUCCESS` and does not do what was asked.** A replacement that reads as a partial update, a setting accepted and discarded, an array entry registered without its value. None of them produce an error, so none would ever appear in a log — and the fix for each is the same: say so in the response, at the moment the caller would otherwise conclude it worked. This is the same failure mode as B-3 (a port reported but never sent), which suggests the question to ask of any write tool is not "does it error correctly" but **"if the server quietly ignores this, would the caller ever find out"**.
- **Suspicion about this family was well founded and is worth reusing.** `cdss_get_kafka_config` was flagged as suspect purely because its two siblings had been wrong, before any evidence about the tool itself — and it was wrong, as were two more in the same section. When one operation name in a service turns out to be invented rather than documented, the rest of that service's section is the right place to look next.

## [1.12.0] - 2026-08-28

> Governance and analytics audit release. Three services' tools were compared one-by-one against every operation in their official API docs — 79 for [Sub Account](https://api.ncloud-docs.com/docs/management-subaccount), 27 for [Data Catalog](https://api.ncloud-docs.com/docs/analytics-datacatalog), 6 for [Resource Manager](https://api.ncloud-docs.com/docs/management-resourcemanager). Backward-compatible — no tool was removed and no parameter was dropped from a schema; the two non-existent parameters are still accepted and now explicitly reported as ignored. ### Fixed
- **`ncloud_detach_policy_from_sub_account` and `ncloud_detach_policy_from_group` sent the policy ID in the URI path — every call failed.** Both built `DELETE /api/v1/{sub-accounts|groups}/{id}/policies/{policyId}` with no request body, but the API takes **no policy ID in the path**: it is `DELETE /api/v1/sub-accounts/{subAccountId}/policies` (and `.../groups/{groupId}/policies`) with the IDs in the body as `policyIdList`. Policy detachment via MCP was therefore entirely broken, while the matching attach tools (same paths, POST) worked. Both tools now send the documented path plus a `policyIdList` body, and gained a `policyIdList` array parameter so several policies can be detached in one call. The old singular `policyId` still works — it is merged into `policyIdList` (deduped) at send time — and a call with neither is rejected before reaching the API.
- **`ncloud_create_role` required `isMyAccount`, a parameter `createRole` does not have.** The API's create-role body is `roleName`, `roleType`, `sessionExpirationSec`, `descCont`, `tags`; `isMyAccount` belongs to a different endpoint entirely — *add Account role target* (`POST /api/v1/roles/{roleNo}/entities/account`). Callers were forced to supply a value that the server ignored, and the parameter implied the tool set the role's target when it did not. `isMyAccount` is now optional and **not sent**, with the description and the dry-run preview's `ignoredParams` naming the endpoint that actually consumes it.
- **`ncloud_create_group` sent `groupDescription`, a field the group resource does not have.** `createGroup` accepts only `groupName` and `tags`, and `getGroup` returns no description either. The value is no longer sent (still accepted, reported under the dry-run preview's `ignoredParams`), and the description points to tags as the way to annotate a group.
- **`ncloud_create_role` mis-documented `sessionExpirationSec`.** It was described as optional and "not allowed for Server type"; the API makes it **required when `roleType` is `Account`**. The parameter is now typed to the four valid values (600 / 1800 / 3600 / 10800) and a missing value on an `Account` role is rejected with a clear message instead of an API error.
- **Three Data Catalog table tools sent camelCase path segments where the API uses kebab-case — every call 404'd.** `ncloud_datacatalog_get_table_partition_keys` requested `.../tables/{tableName}/partitionKeys` instead of **`/partition-keys`**, `ncloud_datacatalog_get_table_schema_and_partition_keys` used `/schemaAndPartitionKeys` instead of **`/schema-and-partition-keys`**, and `ncloud_datacatalog_get_table_schema_versions` used `/schemaVersions` instead of **`/schema-versions`**. A knock-on effect: `ncloud_datacatalog_get_table_schema_by_version` had the right path (`/schema/{version}`) but was effectively unusable, because the only way to discover a version ID is the schema-versions listing that was broken. The file now carries a header note that Data Catalog path segments are kebab-case (`partition-keys`, `schema-and-partition-keys`, `schema-versions`, `run-scanner`), and a test asserts no request path contains any of the three camelCase spellings.
- **`ncloud_resource_list_resources` could not filter by tag key alone.** In `getResourceList`, `tag[].tagValue` is Optional — omitting it matches every resource carrying the key — but the tool's schema made it required, so "find everything tagged `env`" was impossible. Now optional.
- **`ncloud_resource_list_resources`'s `productName` description described the wrong thing, and a field report traced a false "this service has no resources" conclusion back to it.** The API defines `productName` as the resource's **service code** and matches it exactly; the tool's description offered display-name-style examples (`'Server (VPC)'`, `'VPC'`), which leads a caller to pass `Data Query` when the only accepted value is `DataQuery`. The result is zero rows for a service that does have resources — in #6 that nearly produced the conclusion that Data Query is absent from Resource Manager entirely. The description now states that this is the service code (no spaces or parentheses), that every filter in this API is an exact match, and that each returned item carries both `productName` (the code) and `productDisplayName` (the console name) so the valid codes can be discovered by listing without the filter.
- **Data Catalog interpolated database and table names into request paths without URL-encoding them.** Data Catalog's own `createDatabase` spec allows **spaces** in a database name (`[a-z0-9_\-\s]+`), so a database called `my database` produced a request path with a raw space — breaking both the URL and the signature computed over it. All 15 tools that put a name in the path now build it through shared `dbPath()` / `tablePath()` helpers that `encodeURIComponent` each segment.

- **`ncloud_create_role`'s description no longer implies that creating a role grants anything.** It now states that a role is only a container: policies must be attached (`POST /api/v1/roles/{roleNo}/policies`) and a role target set (`.../entities/account` or `.../entities`) — and that neither endpoint has an MCP tool yet.

### Fixed
- **`ncloud_create_snapshot` sent the wrong source-volume parameter name — every call failed.** The tool passed its own input name `blockStorageInstanceNo` straight through to the API, but `createBlockStorageSnapshotInstance` takes the source volume as **`originalBlockStorageInstanceNo`**. Every call therefore returned `900 / Required field is not specified. location : originalBlockStorageInstanceNo.`, regardless of volume state, region, or credentials — snapshot creation via MCP was entirely broken (query/delete snapshot tools were unaffected). The handler now maps the input to `originalBlockStorageInstanceNo` at send time and builds the request params explicitly instead of spreading the raw input.
- **`ncloud_create_snapshot` dry-run previewed a request that differed from the real one.** The preview echoed the input names; it now shows the endpoint and the exact `requestParams` that will be sent, so a wrong parameter name is visible in the preview.
- **Every S3-compatible request with a body now sends `content-md5` — XML-body bucket APIs were entirely unusable without it.** `S3CompatibleClient.request` never attached an integrity header, so Ncloud Storage rejected `ncloud_put_bucket_lifecycle` with `InvalidRequest: Missing required header for this request: Content-MD5 OR x-amz-checksum-*` (reproduced against the live API). The same pattern affected `ncloud_put_bucket_cors`, `ncloud_put_bucket_encryption`, and `ncloud_ncs_delete_objects` — all XML-body calls that had never worked. The client now computes the base64 MD5 of the body and adds `content-md5` **before signing** (so it lands in `SignedHeaders`), skipping injection when the caller already supplied `content-md5` or any `x-amz-checksum-*` header — a case-insensitive check, since a duplicate header differing only in case would corrupt the canonical headers and break the signature. This is a client-level fix, so it covers Object Storage's XML-body tools too. (`ncloud_delete_multiple_objects` in `storage-object.ts` set the header by hand and keeps working — the client defers to it.)
- **`ncloud_ncs_list_objects` returned an empty object list for every bucket.** Its `<Contents>` parser was a single regex that pinned the element order as `Key → LastModified → Size → ETag → StorageClass`, but ListObjectsV2 actually returns **`ETag` before `Size`**, so no entry ever matched: `keyCount` came back correct while `contents` was always `[]`, making populated buckets look empty. The parser now splits `<Contents>` blocks first and extracts each field independently, so element order no longer matters. `parseListBucketsXml` had the same order-pinned shape and was converted alongside it. (Pre-existing defect, unrelated to the rest of v1.11.0 — found while verifying storage classes.)
- **`ncloud_ncs_head_object` did not report the object's storage class**, leaving no way to confirm what class an object was stored in once the list parser failed. It now returns `storageClass` from the `x-amz-storage-class` response header, plus `storageClassHeader` recording whether the header was actually present — S3-compatible services omit it for `STANDARD`, so an absent header is reported as `STANDARD` with that reasoning made explicit rather than silently assumed.
- **`ncloud_put_bucket_lifecycle` offered storage classes that do not exist in Ncloud Storage.** The transition target enum was `STANDARD_IA` | `GLACIER` (AWS S3 class names) and the description advertised `STANDARD`/`STANDARD_IA`/`GLACIER`; the service's `PutBucketLifecycleConfiguration` spec allows only **`ONEZONE_IA`** and **`DEEP_ARCHIVE`** as `Transition.StorageClass`. Every transition rule the tool could produce was therefore invalid. The enum now matches the spec. Callers who previously passed `STANDARD_IA`/`GLACIER` will now get a schema rejection instead of an API rejection — those rules never applied in the first place.
- **`ncloud_create_server` dry-run omitted `networkInterfaceList` and `associateWithPublicIp`.** Both were applied correctly on the real call, but the hand-curated preview object left them out, making it look like they had been dropped. The preview now includes the resolved NIC list (order / subnet / ACGs / IP), `associateWithPublicIp`, and `isProtectServerTermination`.

### Added
- **`ncloud_create_snapshot` gains three parameters** documented by the API but previously unavailable: `originalBlockStorageInstanceNo` (the API's own name for the source volume — accepted as an alias of `blockStorageInstanceNo` and taking precedence when both are given), `snapshotTypeCode` (`FULL` | `INCREMENTAL`), and `regionCode`. Name/description constraints from the doc (3–30 chars, ≤ 1000 bytes) are now stated in the parameter descriptions.
- **Ncloud Storage storage-class selection, including the new `ONEZONE_IA` class.** `ncloud_ncs_put_object` and `ncloud_ncs_copy_object` gain an optional `storageClass` parameter — `STANDARD` (default) | `ONEZONE_IA` (One Zone-IA / Infrequent Access) | `DEEP_ARCHIVE` (Archive) — sent as the `x-amz-storage-class` header per the PutObject/CopyObject specs. Omitting it preserves the previous behavior (no header; the API applies `STANDARD`). `ncloud_ncs_put_object`'s dry-run preview shows the class that will be applied, and `ncloud_ncs_copy_object` reports it in its result. Copying an object onto itself with a different class is how an existing object's class is changed.
- **`snapshotTypeCode` is documented as XEN-only.** Per the Ncloud user guide (*서버 > 스냅샷 생성 (VPC)*), snapshot-type selection exists only on **XEN (Gen2, HDD/SSD)** volumes: `FULL` (default) or `INCREMENTAL`, where an incremental snapshot requires an existing full snapshot of the same volume and is capped at 7 per full snapshot. **KVM (Gen3, CB1/CB2/FB1/FB2) has no snapshot type at all** — the console offers no such choice — so the parameter should be omitted for KVM volumes. The API reference does not carry this distinction; the parameter description and the dry-run preview do (the preview no longer claims "FULL (default)" for an unset type). Description-level guidance only — not enforced in code, since the hypervisor would require an extra lookup per call. Live testing confirmed the API **accepts `snapshotTypeCode: "INCREMENTAL"` on a KVM volume without an error and creates a `FULL` snapshot anyway**, so the description says so explicitly and the dry-run preview raises a `warning_snapshotTypeCode` whenever the parameter is set.

### Changed
- **The shared dry-run message now states that no server-side validation is performed.** `dryRunMessage` (`src/tools/_messages.ts`, used by every `create_*`/upload/apply preview) previously said only "이 요청은 실제 X를 생성하지 않습니다", which read as if the request had been validated. It now adds that the preview checks the input shape only and that a successful preview does not guarantee the real call will succeed — the API is never contacted during a dry run. Affects the preview text of all dry-run-capable tools; no behavior change.

### Notes
- **`CreateMultipartUpload` also accepts `x-amz-storage-class`**, but Ncloud Storage multipart upload is not wrapped by any tool yet (`ncloud_ncs_*` covers buckets, objects, and lifecycle only), so there was nothing to extend there.

It is reported anyway (see Fixed) because live testing left no other way to confirm an object's class, but it is read defensively: an absent header is reported as `STANDARD` with `storageClassHeader` stating the header was missing, so a service that never sends it cannot be mistaken for one that stores everything as `STANDARD`. ## [1.4.0] - 2026-06-14

> Dynamic tool-group loading. **Default behavior is unchanged** — leaving `NCLOUD_TOOL_GROUPS` unset still loads all 1,035 tools, exactly as before. The new behavior is opt-in via `NCLOUD_TOOL_GROUPS=dynamic`.

### Added
- **Dynamic tool groups** — the server can now enable tool groups at runtime, in-session, without a restart. Two always-on meta tools drive it: `ncloud_list_tool_groups` (catalog: 14 groups with services, tool counts, and current enabled/available/blocked status) and `ncloud_enable_tool_group` (activate a group; idempotent; the group catalog is embedded in the tool description so the model can pick the right group without a prior list call). On enable, the group's tools register and the SDK emits `tools/list_changed`.
- **`NCLOUD_TOOL_GROUPS=dynamic`** opt-in keyword — starts with core IaaS groups only (`common` + `compute` + `network` + `database`, ~367 tools / ~65k tokens) instead of all 1,035 (~177k tokens), a 63% context reduction, with every other group one `ncloud_enable_tool_group` call away. Combine with extra groups (e.g. `dynamic,analytics`) to also start them on.
- **Expansion is gated by the `dynamic` keyword.** Listing groups without it (e.g. `compute,network`), or using `all`/unset, is a **locked** state — the model cannot enable more groups at runtime (for strict / least-privilege environments). This replaces the need for a separate disable switch; there is no `NCLOUD_DYNAMIC_GROUPS` env.
- **Security boundary**: a group excluded via `-key` (e.g. `all,-billing`) is also refused for dynamic enable — an operator's intent to withhold a group cannot be reversed by the model at runtime.
- **Notification debounce**: the server is constructed with `debouncedNotificationMethods: ["notifications/tools/list_changed"]`, collapsing the burst of per-tool notifications during a group enable into a single `list_changed` (measured: enabling a 205-tool group emits exactly 1 notification).
- **Tests**: enable flow / idempotency / `-key` block / unknown-vs-moved key / locked-list (no `dynamic`) / full structural invariants re-checked through the dynamic-enable path. README KR/EN gain a "Dynamic groups" section with a client-compatibility table.

### Notes
- list_changed support is client-dependent. Claude Code/Desktop support it; Kiro/Cursor are under real-world validation. If unsupported, the enable response returns a fallback hint (restart with `NCLOUD_TOOL_GROUPS=all`) — i.e. no regression vs. today.
- v2.0.0 (planned) will flip the unset default to the core set and remove the `MOVED_GROUP_KEYS` deprecation shim.

## [1.2.1] - 2026-06-12

> Reliability & internal-consistency patch. No public tool name/schema/group-key changes.

### Fixed
- **MCP server version drift**: the server version is now read from `package.json` as the single source of truth (was hardcoded `1.1.1` in `src/index.ts` while `package.json` was already `1.2.0`).
- **Empty response body on POST/PUT**: `postRequest`/`putRequest` called `response.json()` directly, so a `200`/`201` with an empty body threw `Unexpected end of JSON input` and failed the tool call. All three (`post`/`put`/`delete`) now reuse the hardened `requestRaw` path and return `{ success: true }` for empty bodies. The Cloud-Insight-required `x-ncp-region_code` header is preserved.
- **`ncloud_set_region` only applied to the default client**: region changes are now propagated to every memoized client across all base URLs (Cloud Insight, NKS, Billing, etc.), and newly created clients inherit the current region. The response now documents the scope (not applied: Object/Archive Storage and Cloud Functions — these require a server restart).

### Added
- **Request timeout** (default 30s, override via `NCLOUD_TIMEOUT_MS`): requests no longer hang indefinitely when the gateway is unresponsive; on timeout a friendly message is returned.
- **Automatic retry on HTTP 429** (max 2 attempts, exponential backoff + jitter, honors `Retry-After`). Conservative by design: only 429 is retried (other status codes and network errors are not), and auth headers are regenerated on each attempt.
